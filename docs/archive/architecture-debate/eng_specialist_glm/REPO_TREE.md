# REPO_TREE.md — the target repository tree

Part of the Engineering Specialist F blueprint (`docs/architecture/debate/eng_specialist_glm/`).
The tree is the destination after the three-phase move in REPO_CLEANUP.md. ⚠ marks a folder whose
contents depend on a decision record still to be taken (ADR-0002, 0004, 0006, 0007).

## 1. Six rules that decide where a file goes

1. **Group by what is deployed, not by language.** Everything that becomes a container lives in
   `services/`. The frontend workspace keeps its own root because pnpm and Turborepo need one.
2. **One kind of thing per top-level folder.** Code that runs in production (`services/`,
   `frontend/`), code that trains (`ai/`, `kaggle/`), the database (`database/`), the seam between
   them (`contracts/`), how it runs (`infra/`), what we know (`docs/`, `specs/`), and what we keep
   as evidence (`prototypes/`).
3. **A folder name tells you whether you may edit it.** `prototypes/` is frozen. Everything else
   changes only through a pull request.
4. **Nothing large, nothing secret, nothing generated by hand.** Weights, rasters and datasets
   live in object storage. Secrets live encrypted. Generated files are committed and regenerated
   by `make gen`.
5. **No grab bags.** No `misc/`, `common/`, `shared/` or `helpers/` at any level. A file that fits
   nowhere belongs to the folder that uses it, or it is not needed yet.
6. **The root has files, not clutter.** A new top-level folder needs a decision record.

## 3. Forbidden here

| Folder | Forbidden | Enforced by |
|---|---|---|
| `services/core-api/`, `services/worker/` | model frameworks, weight files, inference in a request | `make check` (import rules), review |
| `services/ai/<family>/` | database drivers and credentials, imports from `ai/` or `kaggle/`, more than one model bundle, PyTorch, CUDA, Triton or TensorRT | image dependency audit, `make check` |
| `ai/`, `kaggle/` | servers, endpoints, operational SQL, credentials, raw datasets, weights | `make check`, secret scan |
| `frontend/apps/*` | `fetch`, `axios`, direct native SDK imports, hand-written API types | ESLint `no-restricted-imports`, `make check` |
| `frontend/packages/api/` | platform code (storage, `expo-*`) | review, lint |
| `database/` | application code, passwords, a table without RLS policies | `database/tests/`, review |
| `contracts/` | hand edits to generated files, two sources for one type | `make gen-check` |
| `infra/` | plaintext secrets, image tags without digests in staging and production, application code | secret scan, review |
| `docs/documentation/`, `docs/team-plan/` | build instructions, architecture decisions, anything that belongs in root docs | `docs/documentation/AGENTS.md` |
| `prototypes/` | any change except a README correction | `CODEOWNERS`, review |
| the whole repository | files over 5 MB, `.env`, datasets, rasters, weights, notebooks with outputs | pre-commit, CI guard job |

## 5. Naming

- Folders and files: lower-case with hyphens (`flood-road-segmentation`), except where a tool
  requires otherwise (`AGENTS.md`, `SKILL.md`, Python modules with underscores).
- Python packages with underscores (`rescuevision_ai`), one distribution per workspace member.
- Migrations: `YYYYMMDDHHMMSS_slug.sql`, one file with a `-- migrate:up` and a `-- migrate:down`
  section (the dbmate format). Timestamps keep two agents from colliding on a number.
- Events: `<subject>.<past-tense-verb>.v<n>.schema.json` (`alert.raised.v1.schema.json`).
- Decision records: `NNNN-short-title-with-dashes.md`.
- Branches and commits: see BRANCHING.md.

## 6. The training layout: `kaggle/<feature-name>/v1, v2, v3 …`

The owner's layout is kept and refined. The refinement is based on how the unmerged branch
`codex/building-damage-v4` already works (thin notebook wrappers, a package pinned by commit,
inputs locked by hash, a submission specification reviewed before upload, run records with SHA-256
for every artifact). That branch is the most mature engineering in the repository; the layout
makes its practice the rule for every feature.

```text

├── README.md                      # how to run, sync, record and promote
├── _shared/
│   ├── bootstrap.py               # the single first cell of every notebook
│   └── dossier.schema.json        # what every vN folder must contain (validated in CI)
└── building-damage/
    ├── README.md                  # task, metric of record, table of versions, which is active
    ├── v1/ v2/ v3/                # archived: the rv_, rv2_ and rv3_ notebooks (mapping below)
    └── v4/
        ├── README.md              # experiment card: hypothesis, change from v3, status, hardware
        ├── kernel-metadata.json   # Kaggle CLI metadata (generated from submit.json)
        ├── notebook.ipynb         # thin wrapper; outputs stripped by nbstripout
        ├── config.yaml            # resolved configuration: package commit, seed, model, recipe
        ├── dataset.lock.yaml      # dataset slugs, versions and SHA-256 of split manifests
        ├── submit.json            # the submission specification, reviewed before any upload
        ├── runs/                  # one JSON per attempt: state, session id, artifact hashes
        ├── metrics.json           # the metrics of record, linked by hash to a run
        └── model_card.md          # intended use, datasets, limits, failure examples
```

### 6.1 Rules that make a version folder worth having

1. **A notebook is a wrapper.** It calls `_shared/bootstrap.py` and one entry point of
   `rescuevision_ai`. It defines no model, loss or metric. Code lives in `ai/` and is pinned by
   commit in `config.yaml`, so the folder runs the same in a year.
2. **Every input is locked.** `dataset.lock.yaml` names each dataset by owner, slug, version and
   the SHA-256 of its manifest. A missing or changed hash stops the run before the GPU is used.
3. **Submission is two steps.** `submit.json` says what will run, where, on which machine, with
   which inputs and whether internet is off. A person approves it. Only then does an agent upload
   it, through the Kaggle API or MCP. No notebook submits anything and no notebook holds a token.
4. **Every attempt leaves a record.** `runs/<run-id>.json` moves through
   `prepared → submitted → running → completed → artifacts_verified → scientifically_reviewed`,
   or ends in `failed`, `cancelled` or `blocked_input` with a reason. A dependent step requires
   both `completed` and `artifacts_verified`. A failed run keeps its record.
5. **Numbers come from one place.** `metrics.json` is copied from a verified run and carries its
   id and hashes. The official scorer is the metric of record for xBD (the team's own notebooks
   contain an approximation that must not be quoted). Test labels never choose a threshold.
6. **Weights never enter Git.** A promoted bundle is written to object storage under
   `models/{task}/{vN}/` with a `manifest.json`, which is the path the report's Table 3-44 already
   reserves for model weights.
7. **A promoted folder is immutable.** Later work is `vN+1`. Only `runs/` may gain records.
8. **Create a feature folder when its first experiment starts**, not before. Empty folders invite
   invented content.

## 7. What not to create

| Do not add | Why | Instead |
|---|---|---|
| a second `README.md` that repeats `AGENTS.md` | two copies drift | link to it |
| a root `utils/` or `helpers/` | grab bags have no owner and no tests | the folder that uses the code |
| a `docs/wiki/` | a second documentation tree | the map in `docs/README.md` |
| per-service `README.md` files that carry rules | rules belong in `AGENTS.md` | one `AGENTS.md` per service |
| a top-level folder named after a person | ownership is in `CODEOWNERS` | `docs/database/` |
| a `vendor/` or copied third-party code | updates are lost and licences are unclear | a pinned dependency |
| timestamped or "final" file names (`report_v2_final.md`) | Git is the version | a commit |
| a monorepo tool for Python (Nx, Bazel, Moon) | one lock file and one task list already cover it | `uv` workspace and `Makefile` |

## 8. Monorepo tooling decision

| Concern | Choice | Reason |
|---|---|---|
| JavaScript workspace and task cache | pnpm + Turborepo (already in `frontend/`) | `turbo run <task> --affected` runs only what changed; Turborepo detects GitHub Actions on its own |
| Python workspace | one `uv` workspace rooted at the repository | "the workspace shares a single lockfile"; `uv sync --frozen` gives every machine and CI the same dependencies |
| Toolchain versions | `mise` | pins Node, pnpm, Python and uv in one file; `mise.lock` records the download URL and checksum of each tool |
| Universal task list | `Makefile` | every agent and every teammate already knows `make`; recipes only call package managers and `tools/` scripts |
| Repository-wide checks | `make check`, the same command locally and in CI | one definition of "passing" |
| Nx, Moon, Bazel | not adopted | a second task graph to maintain for a repository with two package managers; revisit if build times hurt |

Turborepo's affected detection needs git history: check out with `fetch-depth: 0` (the docs
recommend a full history and note that a shallow checkout makes everything count as changed).

| ADR-0002 chooses a TypeScript core (NestJS) | `services/core-api/pyproject.toml` becomes `package.json` and joins the pnpm workspace; `lint-imports` is replaced by an ESLint boundaries rule; the OpenAPI export comes from the framework's decorator. The contract pipeline is unchanged. |
| ADR-0004 puts the worker in the same image as the core | `services/worker/` becomes `services/core-api/worker/` with a second entry point and no Dockerfile; its `AGENTS.md` merges into the core's. |
| ADR-0003 chooses one container per model instead of per model family | `services/ai/` gains one folder per model, all from the same template; `bundle.lock.json` holds one bundle each. |
| ADR-0005 chooses RustFS, or a hosted object store for production | one service in `infra/compose/`; the S3 API is the contract. |
| A GPU is ever bought or rented | a new `Dockerfile.gpu` per AI folder behind a new decision record; nothing else in the tree changes. It is not planned. |

The tree does not depend on which message transport, tile server or offline protocol wins
(ADR-0004, 0006, 0007): those live inside existing folders or as one more service directory.

## 10. The CPU-only host

The owner's constraint fixes one thing that is not open for a decision: the demonstration runs on
one CPU-only Contabo server, for one user at a time. Training happens on free Kaggle or Colab
GPUs. Three parts of the tree exist because of it.

| Part | Why it exists |
|---|---|
| `services/ai/<family>/Dockerfile` (ONNX Runtime or OpenVINO, one pinned bundle) and `ai/export/` | the server runs CPU inference, so every model leaves `ai/` as an exported, measured bundle; PyTorch stays in training |
| `infra/demo/manifest.yaml` and `tools/demo_check.py` | photogrammetry, area-wide analysis and embedding builds are too slow to click live, so they are precomputed and checked by hash before a demonstration (CI_CD.md, section 10.6) |
| `infra/compose/compose.photogrammetry.yml`, off by default | OpenDroneMap runs on CPU when a demonstration is prepared, never on the request path |
| nothing for a GPU, a model server or server-side 3D | there is no GPU to share, so there is no Triton or TensorRT; 3D is drawn in the browser |

The object store is SeaweedFS in `weed mini` mode, with RustFS as the alternative. MinIO, named in
the report's design documents, is not a candidate: its repository is archived (CI_CD.md, section
10.1).
